# P1 implementation evidence

The application remains in English. Contract identifiers remain Indonesian.
Tests use the production Docker app on port 3002 with the existing persistent
volume. No credentials are included in this evidence.

## P1-01

- Only submitted `tidak_baik` findings without a work order are eligible. The
  server assigns high priority / today (Jakarta) for STOP and medium / two days
  ahead otherwise. The text-only Agents SDK agent cannot choose eligibility,
  priority, dates or database IDs. Missing, invalid or failed output falls back
  to `Repair <item name>` and the original finding note.
- A database transaction rechecks eligibility after the model call; concurrent
  requests and repeated POSTs do not duplicate work orders. Creating an open WO
  marks the related finding unresolved while preserving its inspection verdict.
- Real HTTP test: DT-07 produced two specific repair instructions in 6.75s, both
  high priority, open, unassigned and due today. A separate fresh container used
  `OPENAI_BASE_URL=http://127.0.0.1:9/v1`; its POST produced two exact fallback
  titles/actions in 2.42s. Both second POSTs returned `[]`; report filtering passed.
  See work-order-create-check.json. The user's model configuration was unchanged.
- Nine tests cover the prior application plus Jakarta midnight/year/leap-day
  boundaries, priority enforcement, fallback, eligibility, draft rejection and
  concurrent idempotence. TypeScript and production Docker build passed.
- SDK usage follows the installed v0.21.0 interfaces and the official
  [structured-output documentation](https://github.com/openai/openai-agents-js/blob/v0.21.0/docs/src/content/docs/guides/agents.mdx).

## P1-02

- Work-order edits and report finding actions share transaction-backed helpers.
  Completion sets the finding handled and records a timestamp; reopening clears
  the completion timestamp and note. The original inspection verdict and STOP
  remain unchanged. Report-side completion supplies an English default note.
- Production HTTP verification passed in both directions, including repeated
  completion, invalid calendar dates, prohibited fields and missing-order 404s.
  See work-order-sync-check.json. The seed work order was restored to open after
  testing. A simulated database write failure verifies that both records roll
  back together, and stale caller data cannot overwrite a newer assignment.
- All 10 tests and TypeScript passed. The production Docker build succeeded and
  the rebuilt application passed the API checks on port 3002. No UI changed.

## P1-04

  scoped work-order table. The button disables once all findings have orders.
  Each linked finding shows a compact repair card with its title, assignment or
  completion status, and a link to the highlighted work-order row. Report-side
  actions refresh work orders, report queries and the sidebar immediately.
- The report list shows open counts, Not created, Completed or a dash. A mixed
  case with one completed order and another unassigned finding stays Not created;
  it never claims all repairs are complete. Inspector history remains read-only.

## P1 demo continuation

1. Open `/supervisor/laporan`. DT-07 shows two open work orders; DEMO-1/DEMO-2
   show Completed. The sidebar reports two open work orders.
2. Open DT-07's work-order link, assign a mechanic, set a target to yesterday,
   and use Overdue to find it. Complete with a note, then follow its report link
   to see Handled and the green work-order card. The original STOP stays visible.
3. Use Mark unresolved in the finding to reopen its work order. Its completion
   note/timestamp clear and the open count rises. Use the work-order card to
   navigate directly to the highlighted row.
4. To demonstrate creation again, submit another inspection with a Not good
   finding, then choose Create work orders in its report. Existing orders are
   deliberately not deleted or duplicated. The creation browser script accepts
   `REPORT_ID` for a submitted report with one Not good finding and no WO.
