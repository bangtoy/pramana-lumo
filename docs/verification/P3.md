# P3 implementation evidence

Scope: P3-01 through P3-04, in order. All visible copy and Lumo replies are in
English, following the user's application-language instruction. The Indonesian
examples in the ticket describe behavior; Jakarta dates and contract identifiers
are unchanged. Existing inspections, repair work and credentials are preserved.

## P3-01

- Added Analis (Lumo) with four read-only tools using the existing dashboard,
  report-search and work-order rules. Summary output is four lines, report search
  is limited to 15 rows and work-order search to 20, with total counts stated.
  Detail output includes STOP and handled status, without images or agent history.
- Instructions are evaluated per run for current Jakarta dates. The runner uses
  low reasoning effort, eight turns maximum, a 45-second deadline and local
  `pramana-analis` traces grouped by conversation. Sensitive trace data is disabled.
- Structured output validates message, source IDs and up to three recommendations.
  The server removes duplicate/nonexistent sources and limits the message to five
  sentences. The data-recommendation hook uses two suggestions when the model
  supplies none; P3-02 wires the deterministic recommendations into that hook.
- TypeScript and two focused tests pass: tool output/filter behavior, unchanged
  report/order/plan documents, nonexistent source removal and output limits.
  Model-on/off integration is covered with the conversation service in P3-02.

Implementation references: [OpenAI agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents)
and the installed v0.21 SDK types. `outputType` uses the existing Zod dependency;
no new package was added.

## P3-02

- Added deterministic recommendations in the required priority order and all six
  fallback branches. Both English and Indonesian question keywords are accepted;
  replies stay English. Unit codes normalize to DT-07 and latest-report selection
  uses time, not the report list's STOP-first order. Historical reports are not
  presented as proof of today's condition. Mutation requests explain read-only
  scope and never modify fleet records.
- Conversation turns persist in the existing table. A per-conversation lock
  prevents overlapping writes; invalid/missing IDs and empty/oversized questions
  are rejected. Model history is limited to 30 user/assistant messages; visible
  fallback turns remain available when a model returns on the next question.
- Real SDK integration used independent temporary databases, preserving live
  data. With the endpoint set to an unavailable port, DT-07 returned LI-RW-45,
  four recommendations and fallback=true in about 1.6 seconds. With the configured
  model, the answer cited LI-RW-45 and valid work orders; a follow-up resolved
  "that same unit" and identified overdue WO-RW-08. Both real model turns took
  about 16.7 seconds combined. See `analis-integration.json`.
- Reports, orders, plans and models were identical before/after both scenarios.
  Conversation persistence and source existence were checked. Local traces had
  the conversation group ID and contained no API key, photo or evidence text.
  TypeScript and all 26 tests passed, including empty-model-output fallback,
  recommendation order, history bounds and concurrent-turn rejection.
